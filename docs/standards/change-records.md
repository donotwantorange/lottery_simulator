# 变更记录规范

2026-09-22确认：从下一项改动开始执行以下规则。旧文档保留原文件名和实际记录，不机械补齐缺失阶段，不追认未完成的工作。

2026-09-29收紧记录范围：`docs/changes/`只记录代码相关变化，包括功能、规则、配置、接口、结构和对应验收。单纯启停服务、运行状态检查或文字整理不再单独建档；配套使用说明直接维护在操作文档中，必要时补充到相关代码变更记录。除用户明确指定删除的文件外，不批量清理既有历史记录。

| 改动规模 | 文档要求 |
|---|---|
| 小修改：简单代码修复、少量参数调整 | 一份 `YYYY-MM-DD-主题.md`，包含方案、步骤及验证结果；相关文档更新随本记录说明 |
| 较大修改：新功能、结构重构、多模块改动 | 同主题的 `-design.md`、`-plan.md`、实施记录 `.md`，随阶段推进创建，不提前生成空文件 |
| 合并 | 在实施记录中追加；涉及多项改动或复杂冲突时可另建 `-local-merge.md` 并关联 |

## 状态与证据

本节定义如何记录阶段；验证方法和证据强度以[开发与验证规范](development.md)为准。

统一状态为：待确认 → 已确认 → 实施中 → 已验证 → 已合并。仅记录实际到达的阶段；暂停或阻塞作为附注，不伪装成完成。不需要合并的文档工作可以停留在已验证。

- 已验证：约定的本次验收通过，同时列出范围外或尚未完成的检查；如仍缺少本次必需验收，不标为已验证。
- 已合并：已完成本地集成，不等于在线推送或实际部署。
- Git状态单独记录：是否提交、提交号、合并目标及合并号、是否推送。不适用或尚未执行时明确写明，不编造编号。
- 记录规则不构成修改、提交、合并、推送、部署或删除数据的授权。

每项记录应明确：当前状态、目的、确认方案、范围及不做什么、涉及文件、实施步骤或关联计划、实际验证结果、未验事项、Git状态。较大改动以实施记录汇总最新进度，设计和计划互相链接，避免在多份文件重复维护完整过程。

记录长度与风险相称，上述内容可合并表达，不要求逐项设置标题或填写不适用段落。小修改用几句话说明改动、确认方式、结果和必要状态即可，不强制完整日志、截图矩阵或独立报告。同一改动内的小步骤合并记录；已有主题记录可追加，不逐函数、逐文件另建文档。

## 索引维护

在[修改台账](../changes/README.md)为新改动登记主题和链接，阶段变化时同步更新。旧项目按需补充索引，不为填满表格创建空文件，不强制追溯重写历史。

长期开发约定在[规范目录](README.md)维护，具体实现步骤放在设计/计划，实际结果放在实施记录。用户操作步骤放在使用说明中，并以已实现能力为准。
