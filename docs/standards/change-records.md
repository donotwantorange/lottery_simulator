# 变更记录规范

2026-09-22确认：从下一项改动开始执行以下规则。旧文档保留原文件名和实际记录，不机械补齐缺失阶段，不追认未完成的工作。

2026-09-29收紧记录范围：`docs/changes/`只记录代码相关变化，包括功能、规则、配置、接口、结构和对应验收。单纯启停服务、运行状态检查或文字整理不再单独建档；配套使用说明直接维护在操作文档中，必要时补充到相关代码变更记录。除用户明确指定删除的文件外，不批量清理既有历史记录。

| 改动规模 | 文档要求 |
|---|---|
| 小修改：简单代码修复、少量参数调整 | 一份 `YYYY-MM-DD-主题.md`，包含方案、步骤及验证结果；相关文档更新随本记录说明 |
| 较大修改：新功能、结构重构、多模块改动 | 同主题的 `-design.md`、`-plan.md`、实施记录 `.md`，随阶段推进创建，不提前生成空文件 |
| 合并 | 在实施记录中追加；涉及多项改动或复杂冲突时可另建 `-local-merge.md` 并关联 |

## 设计、计划与实施记录的职责

2026-10-08补充：以下是必要信息清单，不是必须逐项填写的长模板。内容简单时合并成短段落；没有涉及的事项不设空章节。简单修改沿用单份记录，不为满足形式额外创建三份文档。

| 文档 | 核心问题 | 维护重点 |
| --- | --- | --- |
| 设计 `-design.md` | 为什么改、最终应是什么样 | 目标、范围、方案、行为与边界、验收标准 |
| 实施计划 `-plan.md` | 按什么顺序把设计做出来 | 任务、依赖、涉及模块、交付结果、集中验收与收尾 |
| 实施记录 `.md` | 实际做了什么、结果如何 | 实际完成情况、偏差、验证结果、遗留事项及Git/部署状态 |

### 设计文档

- 写明当前问题及其依据、目标和本次范围；区分已有行为、静态推断和期望行为。
- 给出选定方案及必要理由。只有存在实际取舍时才比较备选方案，不为每次修改强行列多个方案。
- 说明用户操作、关键状态、数据流或接口契约中受到影响的部分，以及错误和边界处理。数据迁移、权限或部署受影响时再补相应要求。
- 验收标准描述可观察的结果，例如“关闭功能后参数收起，再开启恢复原值”，不在设计中堆叠逐条测试命令。
- 尚未决定、且会影响实施的事项单独列明；不要把假设写成已确认决定。已确认事项不因开始写计划而重复提问。
- 引用适用的长期规范及相关设计，不复制整份规范；设计不包含完整实现代码、每个函数的编辑指令或虚构的验证结果。

#### 章节组织

- 开头简述目标、范围和必要状态信息，避免堆放大量背景、重复说明及历史过程。
- 主章节按需求或功能主题划分，例如“规则编辑体验”“实验提交流程”“服务器更新”，让读者能直接找到某项需求的完整方案。
- 小节描述该需求的具体细节，如显示条件、操作流程、数据/接口变化、异常处理和验收标准；仅列实际涉及的内容，简单要求直接写段落，不强行拆节。
- 同一需求的方案、交互、边界和验收尽量集中在对应章节，避免按前端/后端或方案/交互/错误等维度反复拆散。确实跨需求的公共方案集中说明，其他章节引用。
- 长期共用约定引用规范；跨需求的实施边界、依赖和总体验收放在末尾。设计按“要解决什么”组织，实施计划按“先做什么、后做什么”组织。
- 新需求或审查发现融入相应主题，独立需求才新增章节。修订后的设计保留完整、连贯的当前方案，不长期追加“补充1、补充2、审查问题”等零散章节；问题编号可作为追踪标识，不代替需求主题。
- 标题简短具体，层级连续，避免只有一个短段落也多级嵌套。章节数量由需求决定，不机械套用固定模板；已经归档的历史文档不为统一格式而批量重写。

### 实施计划文档

- 标明所依据的设计、适用范围和必要前置条件；重要的环境或数据限制写清楚，普通操作不扩展成无关准备工作。
- 按能交付的功能或连贯修改单元拆任务，列出先后依赖。不要按每个函数、文件编辑、工具调用或测试命令拆任务，也不按固定任务数量凑步骤。
- 每项任务只需明确：要完成什么、涉及哪些模块/必要文件、依赖什么、交付结果如何判断。涉及关键接口时写清约定，不必预先枚举全部实现细节。
- 将同一功能的关联修改安排为连贯工作；跨模块改造需要交代中间阶段的入口和数据边界，避免新旧代码混用。仅在确有共享状态或协作需要时说明分工，不默认要求子代理或多轮审查。
- 验证集中写入阶段验收安排，按影响面选择必要场景；各任务引用它即可，不重复附整套清单。中途检查只用于排除阻塞或确认高风险前提，遵守开发与验证规范的停止条件。
- 收尾包含受影响的使用说明、实施记录及必要集成工作；提交、推送、部署和真实数据删除标明实际授权边界，不能因写入计划就视为已获授权。
- 计划应足以让执行者理解目标与衔接，但保留常规实现选择空间。用户仅要求设计或计划时，不提前生成实施记录或标记任务完成。

### 实施记录文档

- 在实际实施阶段创建，关联设计和计划，简述已经完成的功能及必要实现偏差。
- 记录实际验证方式、结果、未完成事项和下一步；记录有证据支持的范围，不复制全部命令输出或重复叙述每次编辑过程。
- 修复失败或验收缺口影响结论时如实保留；不把尚未验证的修改标成“已修复”。详细日志或截图仅在复杂问题、关键操作或用户要求时保留。
- 合并、提交、推送和部署分别填写实际状态；设计确认或代码合并不代表功能已经上线。

### 三类文档如何同步

改变目标、业务行为或关键约束时更新设计，再同步受影响计划；任务顺序、文件位置等常规实施调整更新计划即可，实际偏差及结果写入实施记录。无需为不影响方案的细节反复重新确认设计。

计划可标记任务进度，完整实施状态和验证证据集中在实施记录，台账仅维护摘要与链接。后续修订只更新受影响部分，不反复重写全部文档；旧历史记录保持其当时语境。

## 状态与证据

本节定义如何记录阶段；验证方法和证据强度以[开发与验证规范](development.md)为准。

统一状态为：待确认 → 已确认 → 实施中 → 已验证 → 已合并。仅记录实际到达的阶段；暂停或阻塞作为附注，不伪装成完成。不需要合并的文档工作可以停留在已验证。

- 已验证：约定的本次验收通过，同时列出范围外或尚未完成的检查；如仍缺少本次必需验收，不标为已验证。
- 已合并：已完成本地集成，不等于在线推送或实际部署。
- Git状态单独记录：是否提交、提交号、合并目标及合并号、是否推送。不适用或尚未执行时明确写明，不编造编号。
- 记录规则不构成修改、提交、合并、推送、部署或删除数据的授权。

单份改动记录覆盖当前状态、目的和范围、方案/步骤、涉及模块、实际验证结果及必要Git信息。采用设计、计划、实施记录三份文档时，按上文职责分配这些信息，设计或计划阶段不要求填写尚未发生的验证与提交结果。较大改动以实施记录汇总最新进度，设计和计划互相链接，避免在多份文件重复维护完整过程。

记录长度与风险相称，上述内容可合并表达，不要求逐项设置标题或填写不适用段落。小修改用几句话说明改动、确认方式、结果和必要状态即可，不强制完整日志、截图矩阵或独立报告。同一改动内的小步骤合并记录；已有主题记录可追加，不逐函数、逐文件另建文档。

## 索引维护

在[修改台账](../changes/README.md)为新改动登记主题和链接，阶段变化时同步更新。旧项目按需补充索引，不为填满表格创建空文件，不强制追溯重写历史。

长期开发约定在[规范目录](README.md)维护，具体实现步骤放在设计/计划，实际结果放在实施记录。用户操作步骤放在使用说明中，并以已实现能力为准。
