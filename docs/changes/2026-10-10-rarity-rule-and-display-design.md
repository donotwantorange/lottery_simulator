# 稀有度规则扩展与网页显示优化设计

- 日期：2026-10-10。
- 状态：已确认，尚未实施；本文件只记录设计，不修改计算代码或网页代码。
- 目标：新增 `mrfz` 稀有度概率规则，统一软保底说明，修复实验预览统计卡片错位，并整理默认角色池和已有规则名称的显示约束。
- 关联规范：[开发规范](../standards/development.md)、[架构与数据规范](../standards/architecture-data.md)、[界面与交互规范](../standards/ui-interaction.md)、[变更记录规范](../standards/change-records.md)。

## 1. 范围与不做什么

本轮属于规则数据和网页显示的关联改动，沿用现有 Python 计算核心、Django 接口、React 页面和稳定 ID，不新增数据库格式、不改抽样器职责、不引入新的表单框架。

包含：

- 新增规则 `mrfz`；
- 软保底说明改为根据当前参数动态生成的“挖空填写”句式，并同步所有相关说明；
- 修复新建实验预览中“每轮”和“全部轮次”的数字与说明错位；
- 将默认角色池的显示名称改为“zmd默认角色池”；
- 保持已有规则可修改显示名称，并明确名称、ID、修订和历史快照的关系。

不包含：

- 不改变现有概率计算公式、状态推进、随机数消耗或抽样版本；
- 不为 `mrfz` 增加硬保底、赠送池、大保底或周期赠送；
- 不重命名稳定 ID，不批量改写已有历史记录或历史快照；
- 不因本轮规则增加而改变角色池权限、复制署名或实验提交流程。

## 2. `mrfz` 规则

### 2.1 基础稀有度

规则显示名为 `mrfz`，包含四档稀有度，按 rank 从低到高排列：

| 稀有度 | 基础概率 |
| --- | ---: |
| 3星 | 40% |
| 4星 | 50% |
| 5星 | 8% |
| 6星 | 2% |

四档基础概率合计100%。稀有度使用稳定 ID，名称只负责显示；角色池可按现有机制为各档配置角色、UP标记、限定标记和权重。没有角色名单时仍可抽到该稀有度，但不记录具体角色。

### 2.2 六星软保底

`mrfz`只启用六星软保底：

- 用户语义：若连续50次没有获取6星干员，接下来每一次寻访获取6星干员的概率将依次提高2个百分点；
- 现有计算参数：软保底起点为第51抽，即 `soft_start = 51`；每抽增幅为 `soft_step = 0.02`；
- 每次获得6星后按现有状态规则重置相关小保底；
- 概率扣减、上限100%和其他稀有度分布继续使用现有计算代码；
- 不启用六星硬保底，不设置赠送池、大保底或周期直接赠送。

设计中明确区分“连续未获得次数”和“开始提高概率的抽次”：文案中的50不直接作为计算起点保存，避免把用户描述误当成第50抽开始增加。

## 3. 软保底说明统一改造

### 3.1 动态句式

所有软保底相关说明统一使用当前稀有度和当前参数生成，不写死“6星”或“65”等示例值。基础句式为：

> 若连续【软保底起点−1】次没有获取【当前稀有度名称】干员，接下来每一次寻访获取【当前稀有度名称】干员的概率将依次提高【每抽增幅，四位小数】个百分点。

示例：当 `soft_start=66`、`soft_step=0.05`、稀有度名称为“6星”时显示：

> 若连续【65】次没有获取6星干员，接下来每一次寻访获取6星干员的概率将依次提高【5.0000】个百分点。

当 `mrfz` 使用 `soft_start=51`、`soft_step=0.02` 时显示：

> 若连续【50】次没有获取6星干员，接下来每一次寻访获取6星干员的概率将依次提高【2.0000】个百分点。

方括号中的次数和增幅在编辑页是句内输入框，而不只是只读文字；稀有度名称取当前配置，不增加重复的名称输入。对于非最高档，前半句应写“没有获取【该档或更高档】”，与现有获得本档或更高档会重置计数的规则一致。保留简短补充：“增幅单位为百分点，实际概率受低档可扣减概率、更高档机制及100%上限约束。”名称本身已含“干员”时不重复追加。

### 3.2 必须同步的显示位置

不只修改规则编辑器的一处文字，以下已有相关展示统一使用同一参数口径；网页复用共用格式化逻辑，CLI和文档使用一致语义，不要求跨语言共用函数，也不为原本没有说明的位置新增冗余段落：

- 规则编辑页的软保底说明和示例；
- 规则只读摘要及角色池页的规则摘要；
- 新建实验页面选择池后的规则说明；
- 初始条件中与小保底相关的说明；
- 实验预览中涉及下一次触发或当前保底状态的说明；
- 结果、Trace详情中显示保底状态的中文映射；
- 网页操作说明中对软保底的解释；
- CLI或导出中面向用户的规则说明（若该入口展示软保底文字）。

文案统一使用“百分点”，不把 `5.0000%`误写成相对增长率；未启用时显示“软保底未启用”，不继续展示具体生效句式。赠送池软保底若存在，使用“赠送池”范围说明，不能与主池说明混淆。

### 3.3 现有参数与编辑行为

界面填写的是“连续未获得次数”N，不再让用户直接填写内部起点抽次。读写转换只在展示/表单边界进行：

| 内容 | 界面读取 | 保存到现有字段 |
| --- | --- | --- |
| 连续未获得次数N | `soft_start - 1` | `soft_start = N + 1` |
| 增幅（百分点） | `soft_step × 100` | `soft_step = 输入值 / 100` |

因此zmd填写65、保存66；mrfz填写50、保存51。读取后不作修改再保存，原参数不变；不是只换标签却仍让用户输入66。N允许0，表示第1抽即开始提升；须为非负安全整数，且N+1仍满足既有起点约束。清空或非法输入保留草稿并提示，不静默改成0。增幅只读说明通常显示四位小数；编辑和保存不因显示格式舍入原始值，极小正值不能显示为零。

不增加持久字段、不改后端接口、计算代码或历史规则快照。主池和赠送池遵循相同转换，关闭/重开仍保留合法值及待处理错误。初始保底进度和Trace里的真实计数不是起点参数，不能一律减1；JSON导入导出继续保留原字段语义。现有规则的名称、稀有度名称或增幅变化后，草稿说明与预览按现有失效规则更新。

## 4. 实验预览卡片布局

✅ 用户截图已确认：两个卡片的数字与对应说明错行。⚠️ 待实现时核对：标题参与统计网格可能是原因，截图本身不证明具体CSS根因。目标布局为标题独立占一行，统计行固定为“数字＋说明”：

```text
每轮
100      主抽
10       赠送抽
110      总抽
0        直接赠送角色
0        明细事件数
```

“全部轮次”卡片使用完全相同的行顺序和列结构，只替换数字。数字列固定右对齐或按现有中文数字格式对齐，说明列左对齐；长数字允许完整显示，不改变统计口径。窄屏下仍保持每行数字与说明成组，不让标题参与统计网格。

## 5. 名称修改约束

### 5.1 默认角色池

将默认角色池的显示名称从“默认角色池”改为“zmd默认角色池”：

- 保持池 ID、规则引用、角色、奖励和概率不变；
- 默认配置文件、网页选择项、规则摘要和实验预览使用新名称；
- 已保存实验、历史记录和Trace快照保留创建时的旧名称，不批量改写；
- 名称修改只影响新读取或新创建对象的显示，不改变 ID 解析和历史统计。

### 5.2 已有规则改名

已有规则可以修改显示名称：

- 规则 ID、稀有度 ID、角色池引用和计算语义不变；
- 改名属于规则修订，按现有版本冲突检查保存；
- 新实验和新角色池摘要显示新名称；
- 已接受实验及历史快照保留保存时名称；
- 公共规则由管理员修改，私有规则由创建者或管理员修改；
- 名称唯一性、长度、空白和权限继续由现有服务端校验。

## 6. 数据与兼容性

- `mrfz`作为新的规则对象或默认配置，不覆盖 `zmd`，不修改既有规则 ID；
- 规则名称变化不触发池映射，不需要数据库迁移；
- 新规则的角色池引用按现有规则 ID优先、名称仅用于显示/候选确认；
- 历史快照、任务快照和Trace事件不重新计算，不因名称变化重写；
- 如果默认配置文件改名，CLI示例和网页默认选择同步更新，旧文件引用按现有导入/名称候选规则处理；
- 文案格式化只影响页面和说明，不改变随机数消耗、概率向量或抽样版本。

## 7. 验收标准与范围

### 7.1 规则与文案

- `mrfz`四档概率合计100%，六星软保底从第51抽起每抽增加2个百分点；无硬保底和赠送机制；
- zmd现有软保底示例显示连续65次、提高5.0000个百分点；mrfz显示连续50次、提高2.0000个百分点；
- 句内填写65保存为66、填写50保存为51，重载显示原填写次数；不修改保存不改变概率参数，初始进度及Trace真实计数不发生偏移；
- 修改起点、增幅或稀有度名称后，所有相关说明同步变化；关闭软保底后不显示生效句式；
- 规则编辑、只读摘要、池摘要、实验预览、初始条件、结果/Trace和相关说明没有旧口径混用。

### 7.2 预览与名称

- “每轮”和“全部轮次”卡片的每一行均为数字与对应说明，主抽不再错配到赠送抽；
- 桌面、390像素窄屏和等效缩放下统计行不发生错位；
- 默认角色池新显示名为“zmd默认角色池”，ID和历史快照不变；
- 已有规则可改名，公共/私有权限、修订冲突和历史快照符合约定。

本设计只规定行为和验收，不规定具体组件拆分或测试文件。实施前应据此编写对应计划；实现完成后按影响面做定向测试、一次合并后最小本地验收，并将未实施的服务器验收单独记录。
