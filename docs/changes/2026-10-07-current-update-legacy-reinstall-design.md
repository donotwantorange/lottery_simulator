## 2. 部署更新与旧版重装

### 2.1 两条处理路径

| 入口 | 适用情况 | 数据结果 |
| --- | --- | --- |
| 当前版本更新 | 当前受支持的v6部署更新到后续兼容版本 | 保留账号、规则、池、配置、历史、Trace及必要环境，执行数据库迁移 |
| 旧版本永久卸载并重装 | 用户决定放弃旧业务数据，重新使用新版 | 删除明确列出的本项目旧数据，建立空v6数据库并创建新管理员 |

保留安装、卸载、运维、更新四个一级菜单。在更新中提供上述两条路径，复用卸载和安装已有步骤，使旧版重装在一次操作内完成。独立永久卸载仍只负责卸载，不默认立即重装。

本设计不增加兼容性归档重装、旧账号导入、新旧数据卷并行运行或通用历史迁移框架。已有独立运维、保留数据卸载和v6保留卷重装不在本次改造范围内。现有v5导入能力可保留代码及历史说明，但不由这两条新入口调用。

### 2.2 当前版本更新

更新入口与直接 `--upgrade`只接受当前受支持的标准v6源库；v5或更早版本不默认迁移，提示使用旧版永久卸载重装，不能静默切换到删除分支。

继续提供Git快进拉取与使用已下载完整版本两种获取方式。Git拉取要求本目录干净master工作区及预期origin，失败不进入维护；拉取后启动新版脚本执行，避免运行中的旧函数与新文件混用。

更新流程：

1. 核对本机Docker、项目目录、原容器、实际v6路径、卷映射及目标配置，拒绝未知或不兼容源库。
2. 获取并核对完整新版，检查依赖与镜像可用性，记录旧版本。构建前端时不得在旧网站开放期间覆盖其挂载产物。
3. 安排维护，暂停备份调度并确认备份服务结束，停止新请求，等待或取消任务，拒绝未知任务和未完成账号删除；保留冻结后二次检查。
4. 移除旧服务前完成数据库一致性快照与完整旧data、前端、.env及容器/卷映射备份，验证成功并记录私有路径。
5. 仅移除已核对的服务和需重建的网络，保留原数据、备份、证书卷及.env；执行网络预检、安装新版、migrate和健康检查。
6. 验证原账号、连续实验、历史、Trace、取消、可信HTTPS及实际备份；受影响备份链路的恢复验证按第5.2节执行，可复用未受影响的既有证据，不要求每次更新重复完整恢复演练。相关验收通过后再恢复原定时备份。

内部可以复用保留数据移除服务和已有数据安装流程，但不能简单串联当前“保留数据卸载＋全新安装”：前者没有完整数据备份，后者拒绝已有数据。正常更新不重新初始化管理员，不重置密钥、密码或业务。

失败保留旧备份及实际阶段；数据库已迁移后，回退代码不等于回退数据库。不得自动覆盖数据库、删除目标或宣称仅靠重试即可恢复。

### 2.3 旧版本永久卸载并重装

这条入口不需要把旧数据转换给新版，也不需要适配每个历史数据库结构。识别的是项目资源及其归属，不要求旧镜像能创建辅助容器、旧数据库版本受支持、旧任务文件能被新版验证器解析。

最低自动处理范围是同机Docker中可明确归属本安装目录的旧Compose部署。核对项目标签、目录、实际容器及挂载、卷/网络标签和其他使用者；兼容旧服务布局，不强制旧部署恰好拥有新版的app/Caddy两容器。容器缺失时只能清理仍有充分归属证据的残留资源，不能把状态读取失败当作资源不存在。

更早的宿主机Streamlit、手工Python服务、任意绑定目录或归属不明的资源不扫描猜测删除；需要具体清单后另行处理。这是部署资源清理，不是承诺支持所有历史部署方式。

一次重装流程：

1. 获取并核对完整目标版本，检查当前机器能构建/运行新版；尽可能在删除旧服务前发现下载或环境错误。
2. 展示实际旧项目、容器、网络、卷及文件删除清单，明确原账号、密码记录、业务、任务、Trace、备份和证书将丢失，安装后需要新管理员。
3. 提示用户事先另存必要备份；不自动导入或保留旧业务。先输入 `UNINSTALL`，再输入 `DELETE-<实际项目名>`；拒绝确认即不停止或删除旧服务。本文不代替实际执行时的确认。
4. 确认后暂停并停用属于本项目的备份调度，阻止新访问，停止已核对的旧容器和worker，再清理明确归属的资源。由于用户已确认永久删除，不依赖旧任务格式解析；明确说明未完成任务也会终止和删除。
5. 核对清理结果：目标项目无残留容器、被删除的卷及.env已移除，相关端口可用；遇到共享使用者、权限错误或未知状态立即停止，不继续安装。
6. 调用全新安装流程，生成新.env密钥、创建空v6数据库与新管理员，构建和启动新版，重新完成业务/HTTPS及备份验收。

旧镜像缺失时，这条入口可以继续核对资源并请求删除确认；不构建旧镜像、不Docker commit原容器、不尝试恢复旧账号。它以放弃旧数据为前提，不能作为保留数据更新的降级操作。

删除完成后安装失败，旧数据无法自动恢复。报告已删除范围与安装失败阶段，保留新安装现场，不自动再次清理或回滚。只有用户自行保存的有效外部备份可以提供恢复依据。

### 2.4 永久删除的明确范围

| 资源 | 处理 |
| --- | --- |
| 已核对本项目容器及网络 | 停止并移除 |
| 已核对本项目数据、备份、证书及Caddy配置命名卷 | 删除，实际名称先展示；共享或归属不明的卷拒绝删除 |
| 本项目.env与 `/var/backups/lottery/<项目名>` | 删除；固定边界检查，拒绝重定向目录，删除前再次核对 |
| 本项目每日备份timer | 停止并停用；正在执行的备份须先安全结束或明确停止 |
| 备份unit定义、代码、前端产物、Docker镜像及Docker本身 | 保留并提示；重装替换配套前端，备份配置按新版本另行核对 |
| 外部/自定义位置/异机备份、其他项目和任意宿主机目录 | 不自动删除 |

“永久删除”指本项目服务及受管数据，不等于删除所有历史痕迹、卸载Docker或整盘擦除。不增加全机prune、模糊路径删除和无检查强制清理。新安装不能因为旧版本不兼容就放宽首次安装的已有数据保护。

### 2.5 现有实现需要调整的部分

- 当前更新支持v5账号导入，新入口需要限定当前v6正常更新并给旧版明确分流。
- 当前永久卸载先要求标准v5/v6路径和各一个app/Caddy，再调用旧任务预检；旧版永久重装需改为独立的资源归属核对，在双确认后安全停止并删除，不要求数据库或任务格式兼容。
- 当前保留数据卸载检查旧镜像；该保护属于保留路径，不能误用于用户已确认的永久删除重装。
- 复用 `scripts/install.sh`、`scripts/manage.sh`、`scripts/upgrade.sh`及现有备份/构建能力；新行为集中在入口分流、永久删除资源识别和重装串联，不新增数据库迁移、业务格式或依赖。
- 用户操作说明需明确“当前版本更新保留数据”和“旧版重装删除数据”；当前部署指南仍描述已实现行为，实施时再同步，避免提前提供不存在的功能步骤。
- 升级与卸载涉及备份调度时，共用下文R2的归属核验，不能仅凭全局unit名称停止或恢复任务。

### R2：核对备份调度归属

现状与触发：`scripts/upgrade.sh`的`prepare_upgrade()`支持不同安装目录和项目名，但仅凭`lottery-backup.timer`的加载状态就停止该全局unit。若timer属于安装A，升级安装B会暂停A的备份，结束后还会保持暂停。`scripts/manage.sh`已有`management_check_units()`归属检查，可作为统一逻辑的基础。

修复要求：在停止网站、暂停timer或进入破坏性维护前，核对timer关联service、service工作目录、执行命令中的项目/配置和有效unit配置是否属于当前安装。未知、外来或不能可靠识别的自定义配置，应保持原状并停止自动维护，提示人工处理。当前项目未配置timer时允许继续。升级、卸载和恢复调度共用一致规则，只恢复已核对属于当前项目的调度，不新增多项目调度管理框架。

验收：当前项目timer按流程暂停及恢复；无timer仍能继续；其他项目timer、指向其他service、定制覆盖或状态读取失败均在修改服务前拒绝。验证其他项目timer的停止、禁用、恢复命令均未执行。隔离控制流验证与真实systemd验证分别记录。

## 3. 计算与接口修复

本章集中R1、R5、R6和R7；R2在部署章，R3/R4在角色池界面部分。各项静态审查的基准及证据限制统一见第6.2节。

### R1：统一概率尾差处理

现状与触发：`lottery_simulator/rules/definitions.py`的`rarity_vector()`允许概率和与1相差不超过`1e-12`，`runtime.py`原样返回这个向量。`probability.py`抽样时把不足1的尾差落到最后一个正概率选项，`analysis.py`却逐步累积缺失质量。两档概率`0.5`和`0.4999999999995`、关闭全部保底和赠送、角色名单为空、零初始状态、300主抽×1轮，可用于复现理论“状态质量未守恒”。单档概率`0.9999999999995`还可能使等待分析把必出结果当作几何分布。

修复要求：在共享概率计算层对容许误差范围内的向量进行确定性的尾差修正，供抽样、理论递推、等待分析和Trace概率记录共同使用。结果保持非负、有限、总质量守恒，零概率档不能因修正意外获得概率；超出容差的配置仍拒绝。修正应同时覆盖稀有度及角色分布，不能只提高理论守恒容差或只在抽样器中补齐。正常概率配置的规则语义保持一致。

验收：覆盖概率和略小于1、略大于1、精确为1和超出容差；上述300抽实验正常完成；单档等待结果为下一抽必出；确定性抽样边界与理论读取的向量一致；默认zmd的软/硬保底和角色分组结果正常。核对修正是否改变既有种子对应结果；若改变，提升`sampling_version`并更新复现说明，不覆盖历史快照，无需新增版本管理框架。

### R5：统一实验种子输入边界

现状与触发：`dashboard/services/experiments.py`的`_decimal_integer()`手工分块转换整数，导入确认可绕过普通创建接口的种子转换限制。向导入确认接口提交合法池和修订号、5000位十进制种子字符串，在项目默认Python配置下会在JSONField序列化时抛出未处理异常，返回500；事务回滚，不产生半份配置。

修复要求：普通创建、编辑及导入确认共用种子的规范十进制校验与可序列化边界，在昂贵转换和数据库写入前拒绝超长输入，统一返回HTTP 400及中文说明。保留当前允许的正负整数和大于JavaScript安全整数范围的种子精度，不通过全局关闭Python整数保护或吞掉所有异常解决。文件预览、确认和导出应遵守同一边界。

统一边界：

- 项目上限为种子绝对值的十进制表示最多4300位，由一个共享常量维护，不作为实验参数或管理员可绕过的业务限额。负号不计入位数，0按1位计；保留`null`表示自动生成种子的既有语义。
- 有效上限取项目上限与当前Python非零整数十进制转换限制的较小值；运行环境限制为0（不限制）时，项目4300位上限仍然生效。不自动修改全局运行环境限制。网页提示及错误中的上限由服务端有效值决定，前端不独立维护另一套数值；服务与worker部署时使用一致的相关运行配置。
- 十进制字符串只接受ASCII数字和可选的一个前置负号，不接受正号、空白、前导零、指数、小数或布尔值；沿用已有`-0`输入行为，解析为0、输出为`"0"`。网页API保持大整数使用字符串传递的契约，原有安全整数数值输入及配置文件整数格式不变，不经浮点数中转。
- 创建、编辑、实验预览/提交、文件导入预览/确认及导出采用同一服务端校验。字符串先检查位数再转整数；已有整数在转十进制文本或JSON序列化前检查范围，不能先执行可能失败的巨大整数转字符串再捕获兜底。降低环境限制后遇到超限旧值，明确拒绝相关写入或导出，不截断、替换种子或修改原记录。此项不增加历史迁移或改变CLI离线运行的独立契约。
- 超限返回HTTP 400，说明“随机种子最多允许N位十进制数字（负号不计入）”，N为有效上限；格式错误使用对应中文原因。导出在发送下载内容前完成校验，不能先返回部分文件后失败。原有配置文件大小及JSON解析保护继续生效，解析层提前拒绝时返回明确的中文参数错误，不放宽限制或返回500。

验收：复用正常整数、负整数、`null`及超过JavaScript安全范围种子的往返用例；补充有效上限N位（正负均可）接受、N+1位拒绝、非规范输入及5000位字符串拒绝。选择一个低于4300的受支持环境限制验证上限随之收紧，并确认环境限制为0时仍受项目上限约束；环境变更只在隔离进程中进行。覆盖普通创建与导入确认两个不同转换路径，以及导出的序列化边界；共享校验已覆盖的场景不在每个入口机械重复。普通用户和管理员均不能绕过边界；拒绝后无新配置或任务，旧配置及修订号不变，不产生残缺下载。

### R6：校验稀有度映射值类型

现状与触发：`dashboard/services/pools.py`的`_remap_pool_data()`直接对映射值做集合成员判断，API的`JSONField`却允许数组或对象。池编辑或复制请求携带`{"现有稀有度UUID": []}`时会产生`TypeError`并返回500。

修复要求：映射必须为对象，键为有效旧稀有度ID，每个值仅允许目标稀有度UUID字符串或`null`；先校验类型再进行成员查询。保留现有目标存在性、禁止合并冲突和明确清空约束，返回HTTP 400及对应字段的中文错误。服务层也应拒绝不合规调用，不只依靠网页校验。

验收：编辑及复制分别覆盖数组、对象、布尔值、数字、无效字符串、合法UUID和`null`；无效输入均返回400且无副本、原池及修订号不变；合法映射和已确认清空仍可完成。

### R7：CLI显式规则文件参与名称确认

现状与触发：`lottery_simulator/cli.py`的`_load_rule()`在显式文件ID与池引用不同时，先调用目录解析。旧ID不存在、显式文件与引用同名但在规则目录之外时，会在目录搜索阶段失败，无法对已提供的文件进行确认。

修复要求：保留精确ID优先；目录中若已存在引用ID对应的规则，不能用不同ID显式文件替换。精确ID确实不存在时，将显式同名文件作为候选，在交互终端提示名称、ID和路径并确认后使用，再校验池与规则兼容性。拒绝确认、名称不符或非交互环境不能静默替换；正常精确ID匹配不增加额外确认。

验收：目录外同名文件确认成功；用户拒绝及非交互调用拒绝；目录内精确ID优先；名称不符拒绝；确认后的稀有度/角色结构仍须通过编译校验。命令帮助与实际行为一致。

通用显示行为以[界面与交互规范](../standards/ui-interaction.md)为统一依据。第4.3节列出当前机制字段对照，第4.4节对应U1—U8逐页修复，第5.3节列出界面验收；扩展约定不等于本轮新增功能。

### 4.2 采用的长期规范

通用显示状态、优先级、草稿与隐藏字段、操作模式、异步请求、版本冲突、文案数值、扩展及动画约定已集中到[界面与交互规范](../standards/ui-interaction.md)，本设计引用该文件，不再重复维护通用正文。

本轮落实现有页面所需的显示行为及下文U1—U8；复制界面明确准备与保存阶段，优先复用现有接口。未来动画、多语言、插件及新机制仅遵守扩展约定，本轮不新增这些功能。R1—R7的具体缺陷、部署路径和实际验收范围仍在本设计中维护。

### 4.4 逐页修复对应

以下列各页面的具体改动与受影响文件；草稿、错误、权限、格式和异步处理遵守[界面与交互规范](../standards/ui-interaction.md)，不另立页面特例。

#### U1：规则页——按机制展开并解释当前生效内容

涉及`frontend/src/pages/Rules.tsx`及`components/RuleEditor.tsx`。

- 页面按基本信息、稀有度顺序、各档概率与小保底、附加机制组织。每个稀有度的名称、基础概率和两个保底开关放在同一清晰分组中；长说明移到“详细说明”，主概率合计放在对应概率区附近。
- 所有开关遵守4.3节；关闭时不再先陈述“第120抽必得”或“每240抽赠送”再补一句已关闭。启用后才出现按参数生成的说明。
- 软保底示例注明“增加的是百分点；实际概率还受可扣减低档概率及更高档机制约束”，不能把简单相加的示例说成所有配置下都能达到的保证。
- 主池档位改名后，赠送池使用当前同ID档位的显示名称，避免一份规则中出现新旧名称。此项是展示映射，不改变统计ID。
- “查看规则”展示只读摘要及可展开完整参数；切到编辑后才出现输入和适用操作。已引用结构的锁定原因紧邻结构区，复制入口明确。

#### U2：角色池页——区分规则、角色、目标及奖励

涉及`pages/Pools.tsx`、`components/PoolEditor.tsx`、`RuleSummary.tsx`、`RarityMapping.tsx`；同时完成R3/R4。

- 新建池按R3处理可用规则，选择有效规则后再显示对应名单和奖励。无可用规则时给出前往规则页的入口。
- 规则摘要包含基础概率、已启用软/硬保底、大保底阈值/目标/获得后模式、首次赠送和周期赠送；全部使用当前池的显示名。关闭项只显示状态。
- “查看所选规则”定位到该规则的只读详情；通过React路由携带规则ID，由规则页加载并校验访问权限。目标不存在或无权访问时显示明确说明。若离开会丢弃未保存草稿，先提示保留页面或取消导航。
- UP分组关闭时收起占比，但角色UP标记仍保留并可编辑：它还用于分类和机制目标。文案说明“标为UP”和“启用UP概率分组”的区别。
- 自动机制目标显示“UP-A，按最高档名单顺序选中”；指定目标才显示选择框。两种机制都关闭时，目标区只显示“当前无须绑定目标”或收起主体。
- 奖励输入说明“每抽获得该档时附加的数量”，不以“按ID保存”作为主要帮助文字。空角色名单说明“仍可抽出该稀有度，但不记录具体角色”，不笼统当作错误。
- 稀有度映射展示旧档名→新档名、保留/清空的影响；仅在选择清空时展示清空确认。技术ID作为次级详情供排查。

#### R3：解除新建角色池对默认规则的依赖

现状与触发：`frontend/src/pages/Pools.tsx`的`freshPool()`固定复制默认池及默认规则引用；`PoolEditor.tsx`切换规则又要求旧`rule`存在。管理员在删除或改绑引用池后删除默认规则，即使还有其他可用规则，“新建角色池”也无法完成规则选择。

修复要求：新建池可从当前用户有权使用、符合池类型及可见性约束的规则初始化；默认规则存在时可保留当前模板体验，缺失时展示明确的规则选择入口。新建且未绑定有效规则时，选择规则直接建立对应稀有度空名单、显示名/奖励结构；若已有草稿内容会被清除，应明确确认。已有池切换规则仍执行原来的映射或清空确认。没有可用规则时引导先创建规则，不显示无法完成的切换操作。

验收：默认规则存在、默认规则已删除但有其他规则、无任何可用规则三种状态；新选规则的稀有度结构正确，保存及重新读取成功；公共/私有池的规则权限约束仍有效，既有池映射流程保持有效。

#### R4：删除角色时清理表单校验状态

现状与触发：`frontend/src/components/PoolEditor.tsx`将无效权重登记到`invalidFields`，删除角色只移除名单项，没有移除相应标记。例如非目标角色权重改成0后失焦，再删除它，剩余池合法也仍无法保存。

修复要求：删除角色时同步清除该角色全部校验标记；规则映射或清空名单时也清理已不存在的角色标记。名称与权重的校验状态分别管理，不能因为名称修改成功就覆盖仍未修正的权重错误。其余角色尚有错误时，保存仍应阻止。

验收：无效权重→删除该角色→合法池可保存；无效权重→只改名称→仍不可保存；删除一个错误角色而另一个仍错误→仍不可保存；修正全部错误后正常保存，重新读取值与界面一致。

#### U3：实验页——明确预览、运行与保存配置

涉及`pages/NewExperiment.tsx`、`components/ExperimentForm.tsx`、`SimulationPreview.tsx`。

- 操作顺序为选择池→填写参数及必要初始条件→预览→确认运行。已有配置加载、导入和另存入口继续保留；保存配置是独立动作，不提交模拟任务。
- 按钮状态依次为“预览本次实验”“正在生成预览…”“确认并开始模拟”“正在提交…”。预览依据的池、规则、参数或初始确认变化后，显示“参数已变化，请重新预览”，提交按钮回到预览状态。
- 预览按“每轮”和“全部轮次”分组，分别显示主抽、赠送抽、总抽、直接赠送数量和明细条数，避免用连续斜杠让用户对应数字。下一触发位置明确指累计主抽位置；若本轮抽数达不到，标明本次不会触发。
- 池旁展示当前规则简要信息，说明“概率与保底在规则页修改，角色与奖励在角色池页修改”。“修订号”放在次级信息中，涉及版本冲突时再突出显示。
- 明细开关说明“保存每轮每次抽取及直接赠送结果；关闭后仍保存汇总，但不能事后查看逐抽或按抽次分析”。普通用户限额与预览预计条数一并展示；管理员不误显示普通用户业务上限。
- 导入池选择仅展示服务端返回的ID匹配/名称候选；无候选时明确下一步。所选导入池同步驱动其规则和初始条件确认，不能上方选池B、下方仍按池A确认。保留后端二次权限及修订核验。
- 提交结果不明时继续使用本人任务查询和人工选择；任何文案整理都不能改为自动重发提交。

#### U4：初始条件——用实际含义替代内部术语

涉及`components/InitialConditions.tsx`，保留高级区默认折叠及非零状态摘要。

- “历史累计主抽数”补充“本次开始前已完成的主池抽数，不含赠送抽，也不是连续未出高星次数”。符号H只放到详细解释。
- 小保底字段改为“连续未抽到五星或更高的主抽数”等实际档位名称；说明抽到本档或更高会归零，0表示下一抽从第1抽概率开始。
- 大保底按4.3节显示。首次命中后关闭模式已获得目标时，展示“本轮大保底不再生效”；未获得时解释计数从历史主抽数推导。循环模式只输入当前连续未中次数。
- 首次填写非零初始条件时使用“请确认这些初始条件对应当前规则和目标”，不能说目标“从未解析变为UP-A”。只有已有确认依据真正变化时，才展示旧/新名称与模式差异，按钮改为“确认这些初始条件适用于当前规则”。
- 旧目标已不在当前名单时显示“原目标已不在当前名单”，必要时展开旧ID；不能凭相同名称替换或自动清零。无残留数据时不要求清除；残留状态的确认/清除入口在折叠区外可见。

#### U5：任务与结果——中文阶段及明确统计范围

涉及`pages/Results.tsx`、`pages/History.tsx`、`pages/Management.tsx`及`components/ChartPanel.tsx`。

- 统一状态映射：排队中、运行中、已完成、已取消、失败；阶段使用正在模拟、正在计算理论结果、正在保存结果等业务文字。完成状态以服务端为准，不通过模拟计数到达分母推定任务完成。
- 进度显示阶段名、阶段单位及实际计数；模拟步骤如含直接赠送事件，不能标成全是抽数。阶段没有可靠总量时显示正在处理，不伪造百分比或预计完成时间。模拟完成后明确说明理论或保存仍在进行。
- 实验概览分组展示每轮设置、全实验抽取数量、每轮结果均值；赠送次数、赠送角色数量和实际抽数明确区分，不混用“名角色”和“不同角色种类数”。无名单档的角色计数口径提供说明。
- 未开启明细时保留简短的不可用说明与原因，不展示空筛选表单。分类统计选择某来源后，只展示该来源有意义的分类，不能让“直接赠送的奖励”等不适用组合看起来像加载失败。
- 历史重跑继续清楚提示使用当前池/规则以及实际初始条件变化；保存历史的显示名、概率和参数均来自快照，不被当前配置覆盖。

#### U6：过程明细——主表简洁，完整信息按条展开

涉及`components/TraceTable.tsx`、`DownloadForm.tsx`，分页和流式导出保持现有接口。

- 主表保留轮次、事件类型、主池累计抽数、来源、结果、奖励/赠送数量、保底触发及“查看详情”。实际抽次与来源内序号在详情中分别说明；直接赠送不伪装成抽取。
- 每条详情展开各档条件概率、当前角色在该档内的概率、抽前/抽后状态、适用保底及机制。概率用百分比、计数用中文千位格式，必要时提供完整精度；小正概率不能四舍五入后只显示0%。不虚构缺失值，也不改变JSON原始值。
- `first_bonus`、`periodic_grant`等内部值映射为“首次赠送抽取”“周期直接赠送”；普通查看无需辨认代码。未知机制显示“未知机制”并在详情保留原值，不能映射成正常机制。
- 只看直接赠送时隐藏来源及来源抽次筛选，说明“直接赠送没有来源抽次”；只筛选主池或赠送池时提示结果仅包含抽取事件。清除筛选不影响保存的事件。
- 下载按钮说明“下载当前筛选结果”，展示当前匹配条数与适用限额；分页条数不是下载条数。仍由服务器最终核验筛选、权限和限额，前端不能一次加载所有事件。

#### U7：错误、加载与只读操作统一反馈

- 共用字段错误展示，利用`ApiError.fields`定位可识别字段；无字段路径的业务错误显示在对应分组或页首。禁止把后端所有400统一缩成“请求参数无效”，也不猜测未提供的字段归属。
- 页首显示“有N项需要处理”，可定位并展开对应区域；字段旁写具体原因，例如“非UP组分配了50%概率，但名单中没有非UP角色”。修正后清除对应错误，保留其他未修正错误。
- 读取状态明确区分尚未查询、加载中、成功但为空、失败；失败提供重试，保留已有草稿，不能同时继续显示“正在读取”。资源切换时不能把上一个资源的结果当作新资源显示。
- 只读详情用文本和表格；操作权限不足时不铺满灰色编辑控件。因业务约束暂不可操作的按钮，旁边有可见解释，不能只依赖鼠标悬停提示。
- 只有提交期间禁用重复动作；恢复后保留草稿和错误位置。提交成功提示具体保存对象；校验失败不显示成功提示。

#### U8：布局、说明和共用实现

- 复用现有React/CSS，提取实际重复的机制展开区、字段错误/只读值、状态及数值格式化小组件/函数。业务显示条件集中定义并供显示及前端校验使用，服务端仍独立校验；不引入通用表单引擎或新的UI框架。
- 说明分三层：开关旁一句用途、字段旁单位和限制、折叠的完整例子。重要错误不能用细小灰字处理；长段说明限制阅读宽度，窄屏时相关字段按组纵向排列。
- 导航标识当前页面；标题、主要动作和保存结果清晰。机制展开通过原生复选框/按钮和`aria-expanded`等语义表达，收起的输入不留在键盘焦点顺序中；需要修复隐藏错误时展开并定位到对应字段。
- 规则、池及结果详情的字体/间距保持一致；普通信息优先使用名称，ID和修订等排查信息放到次级详情。复用现有图表自适应行为，不因表单整理回退其尺寸和读数功能。

## 5. 实施依赖与验收边界

### 5.1 实施依赖与验证原则

- 部署主线与计算/界面主线可以分别推进、分别记录验收状态；R2随部署改造一起完成，不另维护第二套timer核验。
- 界面先完成共用状态和草稿/错误处理，再依次改规则页、池页、实验与初始条件、结果与明细；R3/R4在U2内一并完成。共用组件只提取真实重复逻辑。
- R6与池映射界面衔接，R5与实验输入及导入错误展示衔接，R1与理论及Trace概率展示衔接；整合时检查接口与口径一致，不重复实现。

审查修复先确认原问题，可复用可信的复现证据；同一功能的相关修改连贯完成后验证修复效果，中途只做排除实施阻塞或高风险前提所需的检查。稳定问题通常以修复前失败、修复后通过确认；仅因果不清、现象不稳定或多因素影响时增加隔离回退或其他对照。按受影响模块做必要回归，整合后集中验收规则→池→实验→结果/Trace流程，不逐个小步骤重复全套测试，不增加SHA核对。检查通过且无新异常或疑点后停止，后续改动只补查受影响部分。R2与部署改造一并验收，其他修复不依赖真实服务器。旧数据、账号或生产资源不用于失败注入。

### 5.2 部署及恢复验收

验证当前v6更新保留账号和业务、迁移顺序正确；旧版本被普通更新拒绝且不自动删除；备份失败不移除旧服务；Git/下载失败不进入维护；不重新初始化已有账号。

验证旧版永久重装不依赖旧镜像或数据库/任务格式；合法旧资源及有明确归属的残留资源可清理；双确认取消不改变服务；其它项目、共享卷/网络、危险路径和状态读取失败拒绝；删除后安装使用空库和新管理员；清理或新安装失败报告实际阶段，不默认重试。测试删除正例只使用隔离临时项目和独立Docker资源，不使用真实业务数据。

先做定向控制流程测试和隔离Compose更新/卸载重装演练，再做服务器业务、可信HTTPS和生产备份验收。此前63项管理菜单检查是旧实现证据，不作为新功能已完成的证明。

备份恢复按影响面验收：本次若改变备份内容、源库/卷映射、迁移顺序或恢复步骤，使用受影响流程生成的备份，在独立临时目录、数据库及Compose资源中恢复；核对原账号可登录、代表性历史和Trace可读，以及小实验结果可正常写入。不将“备份文件生成成功”视为“恢复成功”，不覆盖生产库或用真实数据做失败注入；备份材料按私密数据保护。未受影响且已有可信恢复证据的链路可引用原记录并说明适用范围，不重复完整演练。仅修改timer归属判断时重点验收归属核对及暂停/恢复，不因此强制重跑无关数据库恢复流程。必要恢复检查无法完成时记录原因和未验范围，不将该项标为已验证，也不靠增加无关检查替代。

### 5.3 界面整合验收

| 验收场景 | 必须满足 |
| --- | --- |
| 功能开→填写合法值→关→开 | 输入收起并恢复原值；生效说明同步变化 |
| 关闭后保存→重新加载→开启 | 合法保留参数仍在；关闭期间机制不生效 |
| 无效输入→关闭功能 | 主体收起，明确待处理入口；不能无声丢弃或隐藏阻塞 |
| 切换模式/规则/机制目标 | 只显示当前适用字段；旧初始状态冲突可见、经用户处理 |
| 删除错误角色 | R4错误引用清理；其他角色错误继续可见 |
| 只读/普通用户/管理员 | 展示与权限一致；缺权限不能通过直接API绕过 |
| 多种状态同时出现 | 按界面规范第1节的优先顺序处理；隐藏不覆盖错误，草稿保留不越过访问权限 |
| 切换对象/离开/保存失败 | 未保存修改有明确去留选择；失败保留草稿，成功才更新基准 |
| 准备副本→取消或保存 | 取消无新对象；保存只创建一个副本，原对象和最初署名符合约定 |
| A请求晚于B返回 | 当前选择B只显示B，A响应不覆盖；图表及导入同样适用 |
| 配置版本冲突/权限撤销 | 保留或清理内容按权限处理，不覆盖远端、不自动重提 |
| 预览→改参数→运行 | 旧预览失效，重新预览并明确确认后只提交一次 |
| 读取失败→重试成功 | 无虚假加载/空列表，错误清除，草稿不丢失 |
| 零值/缺失/不适用/无匹配 | 四种含义明确区分，不能统一显示为0或空白 |
| 长名称/重名/极小概率/大整数 | 能识别对象，概率和整数不误显示；历史沿用快照名称 |
| 父子开关/未知机制 | 父关闭子收起，重开保留子原状态；未知能力明确提示且不覆盖数据 |
| 有明细/无明细/只看直接赠送 | 内容及筛选按数据适用性展示，概率/数量口径明确 |
| 任务跨模拟/理论/保存阶段 | 中文阶段与实际状态一致，不提前显示完成 |
| 详情展开、键盘和窄屏 | 可用键盘完成主要操作，焦点可见；无整页横向溢出，必要表格仅局部滚动 |

本表是本轮整合验收范围，不是每个字段或子任务的必跑列表。组件用例应从“关闭字段仍存在但禁用”改为检查收起、恢复、错误处理及请求行为；首次预览不发任务提交，确认后才提交。复用现有用例，选择有意义的代表场景，不穷举所有开关排列、不为每句文案单独增加测试。本轮涉及整体界面布局，连通后集中检查桌面宽度、约390px窄屏、200%缩放和键盘操作，并核实所见页面加载了本次构建；之后局部修订只补查受影响部分。

后续新增功能时复用此验收表，按实际新增能力补充相关项；动画仅在未来实现时验证跳过、重播、关闭与结果一致性，本轮不搭建动画测试或虚构播放入口。
