# 当前版本更新与旧版永久卸载重装设计

- 日期：2026-10-07。
- 状态：按用户要求收紧设计范围；尚未实施。
- 基准：本地master `d4828dc`。本次只整理设计与台账，不修改脚本，不提交、推送或操作服务器；原本地使用手册保持原文。
- 需求：仅保留当前版本的正常更新接口，以及旧版本永久删除后全新安装的入口。

## 1. 两条处理路径

| 入口 | 适用情况 | 数据结果 |
| --- | --- | --- |
| 当前版本更新 | 当前受支持的v6部署更新到后续兼容版本 | 保留账号、规则、池、配置、历史、Trace及必要环境，执行数据库迁移 |
| 旧版本永久卸载并重装 | 用户决定放弃旧业务数据，重新使用新版 | 删除明确列出的本项目旧数据，建立空v6数据库并创建新管理员 |

保留安装、卸载、运维、更新四个一级菜单。在更新中提供上述两条路径，复用卸载和安装已有步骤，使旧版重装在一次操作内完成。独立永久卸载仍只负责卸载，不默认立即重装。

本设计不增加兼容性归档重装、旧账号导入、新旧数据卷并行运行或通用历史迁移框架。已有独立运维、保留数据卸载和v6保留卷重装不在本次改造范围内。现有v5导入能力可保留代码及历史说明，但不由这两条新入口调用。

## 2. 当前版本更新

更新入口与直接 `--upgrade`只接受当前受支持的标准v6源库；v5或更早版本不默认迁移，提示使用旧版永久卸载重装，不能静默切换到删除分支。

继续提供Git快进拉取与使用已下载完整版本两种获取方式。Git拉取要求本目录干净master工作区及预期origin，失败不进入维护；拉取后启动新版脚本执行，避免运行中的旧函数与新文件混用。

更新流程：

1. 核对本机Docker、项目目录、原容器、实际v6路径、卷映射及目标配置，拒绝未知或不兼容源库。
2. 获取并核对完整新版，检查依赖与镜像可用性，记录旧版本。构建前端时不得在旧网站开放期间覆盖其挂载产物。
3. 安排维护，暂停备份调度并确认备份服务结束，停止新请求，等待或取消任务，拒绝未知任务和未完成账号删除；保留冻结后二次检查。
4. 移除旧服务前完成数据库一致性快照与完整旧data、前端、.env及容器/卷映射备份，验证成功并记录私有路径。
5. 仅移除已核对的服务和需重建的网络，保留原数据、备份、证书卷及.env；执行网络预检、安装新版、migrate和健康检查。
6. 验证原账号、连续实验、历史、Trace、取消、可信HTTPS及实际备份，再恢复原定时备份。

内部可以复用保留数据移除服务和已有数据安装流程，但不能简单串联当前“保留数据卸载＋全新安装”：前者没有完整数据备份，后者拒绝已有数据。正常更新不重新初始化管理员，不重置密钥、密码或业务。

失败保留旧备份及实际阶段；数据库已迁移后，回退代码不等于回退数据库。不得自动覆盖数据库、删除目标或宣称仅靠重试即可恢复。

## 3. 旧版本永久卸载并重装

这条入口不需要把旧数据转换给新版，也不需要适配每个历史数据库结构。识别的是项目资源及其归属，不要求旧镜像能创建辅助容器、旧数据库版本受支持、旧任务文件能被新版验证器解析。

最低自动处理范围是同机Docker中可明确归属本安装目录的旧Compose部署。核对项目标签、目录、实际容器及挂载、卷/网络标签和其他使用者；兼容旧服务布局，不强制旧部署恰好拥有新版的app/Caddy两容器。容器缺失时只能清理仍有充分归属证据的残留资源，不能把状态读取失败当作资源不存在。

更早的宿主机Streamlit、手工Python服务、任意绑定目录或归属不明的资源不扫描猜测删除；需要具体清单后另行处理。这是部署资源清理，不是承诺支持所有历史部署方式。

一次重装流程：

1. 获取并核对完整目标版本，检查当前机器能构建/运行新版；尽可能在删除旧服务前发现下载或环境错误。
2. 展示实际旧项目、容器、网络、卷及文件删除清单，明确原账号、密码记录、业务、任务、Trace、备份和证书将丢失，安装后需要新管理员。
3. 提示用户事先另存必要备份；不自动导入或保留旧业务。先输入 `UNINSTALL`，再输入 `DELETE-<实际项目名>`；拒绝确认即不停止或删除旧服务。本文不代替实际执行时的确认。
4. 确认后暂停并停用属于本项目的备份调度，阻止新访问，停止已核对的旧容器和worker，再清理明确归属的资源。由于用户已确认永久删除，不依赖旧任务格式解析；明确说明未完成任务也会终止和删除。
5. 核对清理结果：目标项目无残留容器、被删除的卷及.env已移除，相关端口可用；遇到共享使用者、权限错误或未知状态立即停止，不继续安装。
6. 调用全新安装流程，生成新.env密钥、创建空v6数据库与新管理员，构建和启动新版，重新完成业务/HTTPS及备份验收。

旧镜像缺失时，这条入口可以继续核对资源并请求删除确认；不构建旧镜像、不Docker commit原容器、不尝试恢复旧账号。它以放弃旧数据为前提，不能作为保留数据更新的降级操作。

删除完成后安装失败，旧数据无法自动恢复。报告已删除范围与安装失败阶段，保留新安装现场，不自动再次清理或回滚。只有用户自行保存的有效外部备份可以提供恢复依据。

## 4. 永久删除的明确范围

| 资源 | 处理 |
| --- | --- |
| 已核对本项目容器及网络 | 停止并移除 |
| 已核对本项目数据、备份、证书及Caddy配置命名卷 | 删除，实际名称先展示；共享或归属不明的卷拒绝删除 |
| 本项目.env与 `/var/backups/lottery/<项目名>` | 删除；固定边界检查，拒绝重定向目录，删除前再次核对 |
| 本项目每日备份timer | 停止并停用；正在执行的备份须先安全结束或明确停止 |
| 备份unit定义、代码、前端产物、Docker镜像及Docker本身 | 保留并提示；重装替换配套前端，备份配置按新版本另行核对 |
| 外部/自定义位置/异机备份、其他项目和任意宿主机目录 | 不自动删除 |

“永久删除”指本项目服务及受管数据，不等于删除所有历史痕迹、卸载Docker或整盘擦除。不增加全机prune、模糊路径删除和无检查强制清理。新安装不能因为旧版本不兼容就放宽首次安装的已有数据保护。

## 5. 现有实现需要调整的部分

- 当前更新支持v5账号导入，新入口需要限定当前v6正常更新并给旧版明确分流。
- 当前永久卸载先要求标准v5/v6路径和各一个app/Caddy，再调用旧任务预检；旧版永久重装需改为独立的资源归属核对，在双确认后安全停止并删除，不要求数据库或任务格式兼容。
- 当前保留数据卸载检查旧镜像；该保护属于保留路径，不能误用于用户已确认的永久删除重装。
- 复用 `scripts/install.sh`、`scripts/manage.sh`、`scripts/upgrade.sh`及现有备份/构建能力；新行为集中在入口分流、永久删除资源识别和重装串联，不新增数据库迁移、业务格式或依赖。
- 用户操作说明需明确“当前版本更新保留数据”和“旧版重装删除数据”；当前部署指南仍描述已实现行为，实施时再同步，避免提前提供不存在的功能步骤。

## 6. 最低验收与实施边界

验证当前v6更新保留账号和业务、迁移顺序正确；旧版本被普通更新拒绝且不自动删除；备份失败不移除旧服务；Git/下载失败不进入维护；不重新初始化已有账号。

验证旧版永久重装不依赖旧镜像或数据库/任务格式；合法旧资源及有明确归属的残留资源可清理；双确认取消不改变服务；其它项目、共享卷/网络、危险路径和状态读取失败拒绝；删除后安装使用空库和新管理员；清理或新安装失败报告实际阶段，不默认重试。测试删除正例只使用隔离临时项目和独立Docker资源，不使用真实业务数据。

先做定向控制流程测试和隔离Compose更新/卸载重装演练，再做服务器业务、可信HTTPS和生产备份验收。此前63项管理菜单检查是旧实现证据，不作为新功能已完成的证明。

本次仅更新设计与索引，没有新增空计划或执行记录，没有修改脚本，没有执行真实更新、卸载、安装或删除。后续用户要求实施时再制定具体计划。
