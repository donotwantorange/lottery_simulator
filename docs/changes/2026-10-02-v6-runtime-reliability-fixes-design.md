## 2. R1：区分不存在与状态暂时不可读

### 2.1 共享读取契约

在 `dashboard/jobs.py` 的共享读取入口处理，不能只给详情接口加重试。沿用临时文件、flush/fsync、os.replace发布方式，不改成原地覆盖，不通过减少落盘或取消语义校验绕开问题。

| 读取结果 | 共享入口结果 | 对外行为 |
|---|---|---|
| 状态读取成功且结构、目录ID匹配 | 返回合法JobState | 按现有所有权、auth_version和操作权限检查 |
| 非法UUID/越界路径，或有界重读后任务目录确实不存在 | 返回None | 真正不存在/不可访问仍404 |
| 状态文件短暂FileNotFoundError、ENODATA（实测errno61）等已识别瞬态I/O | 有界重读 | 成功则正常响应，不提前返回404 |
| 瞬态重读耗尽、已有任务目录却缺少状态、权限或其他I/O错误 | 抛出专用状态不可用异常 | 认证后映射503、现有code=storage_busy |
| 状态JSON/版本/字段校验不合法 | 不返回合法状态，不伪装不存在 | 状态不可用并记诊断；阻止依赖该状态的写操作 |

最多读取3次，瞬态失败后的退避为10ms、20ms，额外退避合计30ms，不含文件系统调用自身耗时。权限失败等明确非瞬态错误直接失败，不忙等、不无限重试。最终缺失判断自身若读取元数据失败，也必须归为不可用，不能仅根据exists返回值推断任务不存在。

只增加一种明确的“任务状态不可用”异常，内部保留I/O/损坏原因供日志诊断；API返回固定中文信息，不返回文件路径、JSON、owner、seed或内部异常。认证检查在读取前完成；读取成功后仍检查资源所有权。无法确定状态时绝不授权读取结果、取消、重存或删除。

### 2.2 枚举与调用方

当前多处 `glob("*/state.json")` 可能在状态文件替换时直接漏掉目录，单独修复get不足以覆盖。复用共享的任务目录枚举：以规范UUID任务目录为候选，再通过同一读取入口取状态；不跟随符号链接。发现规范UUID名的符号链接或不安全目录时按不可用拒绝写操作，不将它跳过后认定空闲。不新增任务注册表或缓存。

- 全局准入/get_active/_active_states、重启协调和reap：不能跳过不可读任务后认定空闲；保持全局锁顺序，未知状态时拒绝启动第二个worker、误判已停止或清理文件。
- worker启动、进度、取消、提交和终态写入：耗尽重读时不得把不可用误判为已取消；保留可恢复文件并记录错误。若数据库已提交但终态发布失败，沿用已有按run_id和完整快照协调恢复机制，不再提交一遍实验。
- 本人任务/管理任务列表、busy、详情、结果/Trace读取、取消、重存：统一处理不可用。列表不能静默遗漏一个不可读候选；busy不能返回false。GET可返回503；有副作用请求失败后由用户核实状态，不自动重放POST。
- 账号删除预览和执行：无法确定任务清单时拒绝继续；预览不显示不完整计数，首次删除不能先标deleting再跳过未知任务。已进入删除流程时保留原删除清单和可重试状态，不删除未知目录。
- `run_job`管理命令：不可用时报告失败，不将其当作任务不存在而静默退出。批量扫描同样复用入口。

持续损坏的规范UUID任务目录需要运维明确处理；本轮不设计自动删除、隔离或强停未知进程。对不可读状态更保守地拒绝准入是预期行为，须调整原“无效状态直接忽略”的相关用例。

### 2.3 页面重试语义

现有轮询对网络错误和5xx重试的节奏保持：可见页面2秒、隐藏页面10秒；保留上一次合法状态及进度，显示可恢复错误。真正401/403/404继续停止对应轮询，不把所有404改成重试来掩盖不存在或越权。

## 3. R2：查询数字安全转换

分页与池/规则/实验导出修订号统一使用一个查询整数转换入口，复用现有分页上限和修订号校验。涉及 `dashboard/api/pools.py`、`rules.py`、`experiments.py`；分页入口的任务/管理/实验列表同步受益。

- 转换前校验文本类型、非空、十进制数字，最长1024字符；超过长度或int转换失败均抛现有API参数异常并返回400。
- 保持现有正数/分页上限及修订号校验；正常前导零不额外禁用，但仍受文本长度限制。缺失分页继续用默认值，缺失修订号仍400。
- 真正资源不存在/越权仍404，合法但过期的修订号仍409。所有参数均需完成校验后再进入资源操作。
- 不修改Python整数转换全局限制，不放宽请求大小限制，不改变任意精度seed、数量字符串或配置JSON的契约。

5000位输入必须被应用层明确拒绝；生产入口提前返回414也允许，但不能依赖代理长度限制保护直接调用和开发环境。

## 4. R3：轮询错误恢复

`frontend/src/pages/Results.tsx` 将状态轮询错误与现有列表/结果/取消操作错误分开，增加最小的独立pollError状态即可，不引入统一请求管理器。

成功且仍属于当前job/user/session的状态响应只清除pollError；失败轮询只更新pollError并按现有条件安排一次后续查询。轮询成功不能清除结果读取、列表或取消POST失败的提示。

切换job、账号或session时重置对应上下文错误；保留AbortController与stopped校验，旧响应不得覆盖新任务。每个上下文最多一个定时器，请求未完成时不重叠启动轮询。completed之后不继续查状态；真正终态404不重试。任务自身error/persistence_error/cleanup_error保持原展示，不因GET恢复而消失。

## 5. R4：保存与提交阶段真实、有序

当前commit_guard先发布committing，然后repository事务中的保存回调又发布saving。修复只调整阶段通知位置，不能移动全局锁或把数据库导入移出原子事务。

保留顺序：模拟simulating → 理论theory → Trace校验validating（有Trace时）→ 保存saving → 提交committing → completed。

- commit_guard仍在原位置取得全局锁，校验状态与取消，覆盖整个repository事务及终态发布；进入guard时保持saving，不提前发布committing。
- `HistoryRepository.save_run`复用保存progress_callback报告saving。新增一个可选before_commit回调，在最后批次写入成功、计数检查和未缓存取消检查完成后，紧邻最外层transaction.atomic退出前通知committing。回调之后再做最终取消检查，事务内异常仍回滚。
- matched run_id的幂等分支也经过同一提交前通知/检查边界；不相同快照仍拒绝。没有回调的现有调用保持原行为，不改变返回值和存储格式。
- 最后保存进度total/total只能在最后批次写入本事务后发布；其含义是本事务已写入，只有事务成功退出才称历史已保存。committing不再发布saving进度，不伪造百分比或ETA。
- commit_guard在repository事务成功退出后才发布completed/history_saved/run_id；取消、事务失败或状态发布失败按原恢复规则处理。状态通知失败不能留下部分历史。

取消与提交竞争的边界不变：取消接口仍使用同一锁；结果只允许完整保存或完整取消，不允许cancelled同时存在本轮新历史。新增回调用于显示真实阶段，不承担授权或重新组织事务的职责。

## 7. R6：明确代理身份与来源信任

### 7.1 当前拓扑和选择

按当前项目直连公网客户端→Caddy→app的单层代理拓扑设计。客户端经同一NAT使用相同公网IP仍共享来源桶，这是既有规则；本修复防止不同真实来源全部被折叠成Caddy地址。

选择Compose专用后端网络和固定Caddy IPv4，复用现有精确IP可信代理设置。固定IP由网络配置分配，不从一次docker inspect结果复制；不引入CIDR信任、DNS轮询、共享鉴权头或trust-all开关。

- app只加入专用backend网络，不发布宿主机8000端口；Caddy同时加入对外网络与backend，保留HTTPS/证书签发所需对外能力。
- backend设置明确IPAM子网、internal=true，Caddy在该网络使用固定ipv4_address。`LOTTERY_PROXY_SUBNET`和`LOTTERY_CADDY_IP`可由.env指定，Compose提供配套默认示例`172.30.96.0/24`、`172.30.96.2`。这些是设计默认值，不表示当前服务器已检查或应用。
- backend另设`LOTTERY_PROXY_DYNAMIC_RANGE`，默认`172.30.96.128/25`，由Docker原生IPAM ip_range分配app动态地址；范围必须是子网内规范IPv4范围，排除Caddy固定地址并留有app地址。2026-10-02真实容器已复现：不限制动态范围时，先启动的app占用`.2`，Caddy静态地址启动冲突。另显式设置`LOTTERY_PROXY_GATEWAY`（默认`172.30.96.1`），防止Docker根据动态池自动选择`.128`网关；校验其成员关系、规范形式及与网络/广播/Caddy地址不冲突。复用网络必须核对IPRange和Gateway一致，不能复用旧配置。Docker内置host/none网络的IPAM.Config可为null，仅表示没有独立IPAM网段，仍检查全部主机路由。
- app的`LOTTERY_TRUSTED_PROXIES`由同一个`LOTTERY_CADDY_IP`注入，不能独立配置成另一个不匹配的容器地址。启用前检查IP属于子网且不是网络/广播/保留网关地址，核对现有Docker网络和主机路由冲突；冲突时停止并提示调整，不删除网络或卷。
- Caddy明确将上游X-Forwarded-For覆盖为它看到的连接对端单个IP（`{remote_host}`），不沿用或追加客户端提供的链。其上游选择app所在backend，使app收到的REMOTE_ADDR等于固定Caddy地址。
- 应用设置解析可信列表时去空白并规范化IP；非法IP、通配符、CIDR或主机名直接拒绝配置。默认开发模式仍为空列表，未经显式信任的头始终无效。

Caddy支持上游请求头重写与remote_host占位符，Compose支持服务静态地址和网络IPAM；具体配置需经验证后实施。依据：[Caddy反向代理请求头](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers)、[Caddy占位符](https://caddyserver.com/docs/caddyfile/concepts#placeholders)、[Compose服务静态地址](https://docs.docker.com/reference/compose-file/services/#ipv4_address-ipv6_address)、[Compose网络](https://docs.docker.com/reference/compose-file/networks/)。

### 7.2 登录与部署边界

保留账号5次失败/15分钟和来源20次失败/15分钟的既有策略，不清真实LoginLimit，不提高阈值来掩盖来源识别问题。可信代理重写头非法时仍保守使用unknown桶，不接受客户端任选IP。

本机Windows临时代理不自动设为可信，不将设计例子用于真实环境。若增加CDN、负载均衡或多层代理，必须另行明确可信链；不能直接把本方案中的连接对端当作终端用户IP。

本轮设计不触发服务器配置更新或容器重建。正式应用时保留原数据卷/.env/证书；仅重建必要服务网络，禁止down -v。重建后验证代理地址、HTTPS、来源桶分离和重启稳定性；失败回滚原配置，并明确旧配置仍有共享桶限制，不用信任全部来源救急。


## 8. R7：规则编辑布局与简明说明

2026-10-02用户补充三项要求：基本信息与权限移到选项上方；明确稀有度高低方向并补充选项说明，重点解释大保底；角色池大保底目标括号文案改为“（规则使用最高稀有度中排序第一的UP）”。仅改展示与说明，不改变参数、名单顺序、目标解析、概率或保底行为。

### 8.1 基本信息和等级方向

- `Rules.tsx`目前先渲染名称/类型/可见性字段，`RuleEditor.tsx`随后才显示“基本信息与权限”空标题及“在此页面外编辑”提示。将真实字段包装成一个基本信息section，标题在名称/类型/可见性之前；删除RuleEditor中的重复空section。新建、编辑、详情采用同一顺序，不用CSS order仅改变视觉位置。
- 编辑区域顺序：基本信息与权限 → 稀有度及高低顺序 → 基础概率与小保底 → 大保底 → 首次赠送池 → 周期直接赠送 → 规则摘要。
- 现有列表按rank升序，上方较低、下方较高。保持排序逻辑，在标题下常驻说明“从上到下，稀有度等级逐渐升高；最上方最低，最下方最高”。首尾行分别标“最低稀有度”“最高稀有度”；只有一档时标“唯一稀有度”，不同时显示相反标签。
- 上移降低等级，下移提高等级；移动后首尾标记随实际顺序更新。说明“顺序决定保底中的高低比较，基础概率另行填写”，不声称等级高就自动拥有更低概率。
- 已引用的结构锁和只读/忙碌禁用规则保持；类型及权限仍由父页面和后端校验，普通用户不能因此新增公共规则或编辑他人规则。

### 8.2 各组选项说明

采用每组选项一两句、关键字段就近提示的形式。大保底的两种获得后模式按当前选择显示短说明；不用长篇弹窗或新帮助组件框架。具体阈值示例由当前输入生成，不硬编码默认参数。

| 选项组 | 必须说明的内容与示例口径 |
|---|---|
| 基本信息与权限 | 名称便于识别；公共规则由管理员创建/维护；私有归创建者所有。私有公开可见允许其他用户查看/绑定，不能理解为所有人都能编辑；管理员权限保留 |
| 基础概率 | 百分比是每次常规抽取的初始概率，各档合计100%；保底触发后本次概率可能改变。按稀有度名称配置，不按名称字面推断等级 |
| 软保底 | 勾选明确称“启用软保底”，避免仅称“启用小保底”。连续未抽到该档或更高档时，从起点抽次提高概率；单位为百分点。例如0.8%增加5个百分点得到5.8%，不是乘以1.05；实际说明按当前起点/增幅更新 |
| 硬保底 | 连续N−1次未抽到该档或更高档时，第N次保证该档或更高档；抽到同档/更高档重新计数。最高档没有更高档，按同一规则解释 |
| 大保底抽数 | 只看主池是否抽中目标，不是“抽到任意UP”。连续N−1次主抽未中目标，第N次主抽必得目标；提前抽中也会触发所选获得后模式 |
| 大保底目标 | “最高稀有度名单中的第一个UP角色（由角色池确定）”。不是首次随机抽出的UP、权重最大的UP或名单第一行未标UP的角色 |
| 大保底一次模式 | 标签/说明明确“本轮主池抽中目标后关闭”。本轮后续不再启用大保底，下轮按该轮初始条件重新开始；不是把整条规则永久关闭 |
| 大保底循环模式 | 标签/说明明确“每次主池抽中目标后重新计数”。命中目标后未中计数归零，大保底继续有效；再次达到N次未中时仍保证目标 |
| 首次赠送池 | 每轮在累计主抽跨过触发位置时额外抽指定次数，只触发一次；赠送抽有独立概率/保底，不消耗或推进主池抽数/保底。非零初始历史已越过触发位置时不补发 |
| 周期直接赠送 | 每累计N次主抽直接获得指定数量，不进行抽取；不增加真实抽数、不消耗随机数、不计抽取奖励，也不改变主池保底状态。UP自动目标与池指定目标分别解释 |
| 机制关闭/结构锁 | 关闭后相应参数不生效，已有值保留；引用结构锁需复制规则再调整，不让帮助文案暗示仍可重排 |

大保底只由主池抽中目标更新；赠送池抽到目标或周期直接赠送得到目标都不会关闭/重置主池大保底。说明要明确这一点，避免把当前“获得目标后”泛化为任意来源获得。

常驻说明用普通文本，字段与说明可用aria-describedby关联；不要把所有说明设为实时播报。数字错误仍由原校验提示处理，文案调整不改变JSON字段/枚举值。

### 8.3 角色池目标文案

`PoolEditor.tsx`大保底目标行保留已解析角色名，括号精确替换为用户要求的“（规则使用最高稀有度中排序第一的UP）”。补短提示：“按这一档角色名单从上到下选择第一个标记UP的角色，与权重大小无关。”未解析时继续提示在最高稀有度标记UP。

该替换仅用于大保底，不统一覆盖周期赠送：当前周期赠送first_up按稀有度由高到低查找第一个UP，最高档没有UP时可继续查找低档；只有pool_selected才用角色池指定角色。规则编辑中的自动赠送目标说明和RuleSummary相关措辞也要与这一口径一致。

调整角色名单顺序可能改变自动目标，仍按现有修订/初始上下文确认及冻结快照机制处理；不自动重写已完成历史或正在运行任务。最高档有两个UP、首位普通角色、权重与顺序不同、最高档无UP但低档有UP等用例用于验证文字和实际解析一致。低档回退用例需关闭大保底，否则其最高档目标约束会使池不合法。
